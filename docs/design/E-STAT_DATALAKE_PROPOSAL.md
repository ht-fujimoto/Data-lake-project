**作成日**: 2026年2月3日

## 1. エグゼクティブサマリー

E-statオープンデータをAPI経由で取得し、S3にIceberg形式で格納する自社データレイクを構築します。本提案では、検索機能を中心に据えた設計アプローチと、データの完全性を保証する動的スキーマ方式を推奨します。

### 主要な推奨事項

1. **データセット単位の動的スキーマ** を採用（従来の11ドメイン固定スキーマではなく）
2. **ハイブリッド検索アプローチ** を採用（メタデータ検索 + Athena）
3. **時間フィールドはSTRING型 + 補助カラム** で保存（TIMESTAMP型ではなく）

## 2. データレイク設計の選択肢

### 2.1 スキーマ設計

#### ❌ 従来アプローチ: 11ドメイン固定スキーマ

```
構造:
├─ population_data (全人口データセットを1テーブルに統合)
├─ economy_data
├─ labor_data
└─ ... (計11テーブル)

問題点:
✗ データセット固有のカラム（@cat04, @cat05など）が失われる
✗ 情報の損失が発生
✗ 新しいデータ構造に対応できない
```

**具体例:**
```python
# 元データ: 10カラム
{
  "@time": "2020",
  "@area": "13000",
  "@cat01": "総数",
  "@cat02": "男性",
  "@cat03": "20-24歳",
  "@cat04": "未婚",      # ← 失われる
  "@cat05": "大卒以上",  # ← 失われる
  "$": "12345"
}

# 固定スキーマ変換後: 8カラム
{
  "year": 2020,
  "region_code": "13000",
  "category": "総数",
  "value": 12345.0
  # cat02-cat05の情報が失われる
}
```

#### ✅ 推奨アプローチ: データセット単位の動的スキーマ

```
構造:
├─ dataset_0003411168 (国勢調査 - 独自スキーマ)
├─ dataset_0003109687 (労働力調査 - 独自スキーマ)
├─ dataset_0003103532 (GDP統計 - 独自スキーマ)
└─ ... (データセットごとに最適化されたテーブル)

+ メタデータカタログテーブル (検索用)
  └─ dataset_catalog
```

**メリット:**
- ✅ すべてのカラムを保持（情報損失ゼロ）
- ✅ データセット固有の構造を維持
- ✅ 新しいデータ構造に自動対応
- ✅ バッチ処理も問題なく実装可能

**デメリットと対策:**
| デメリット | 対策 |
|----------|------|
| テーブル数が多い | メタデータカタログで一元管理 |
| クロステーブル分析が複雑 | ビューで対応 |
| 管理コスト増加 | 自動化ツールで管理 |

## 3. 検索ツールの選択肢

### 3.1 選択肢①: AWS既存ツール

**主なツール:**
- Amazon Athena + AWS Glue Data Catalog
- Amazon OpenSearch Service

**メリット:**
- ✅ マネージドサービスで運用負荷が低い
- ✅ スケーラビリティが高い
- ✅ Icebergとの統合が標準サポート
- ✅ 初期開発コストが低い

**デメリット:**
- ✗ カスタマイズ性が限定的
- ✗ クエリコストが従量課金（Athena: スキャン量課金）
- ✗ 日本語キーワード変換などの独自ロジックは別途実装が必要
- ✗ ベンダーロックイン

**コスト:** 月額 $50-100（100件規模）

### 3.2 選択肢②: 自社検索ツール

**アーキテクチャ:**
```
メタデータカタログ (JSON/Parquet)
  ├─ データセット情報
  ├─ スキーマ情報
  ├─ キーワードインデックス
  └─ 統計情報

+ キーワード変換辞書
  └─ 日本語 ⇔ 英語、同義語マッピング
```

**メリット:**
- ✅ 完全なカスタマイズ性
- ✅ 日本語特有の処理を最適化可能
- ✅ コスト最適化（メタデータ検索は無料）
- ✅ 検索ロジックの改善・学習が可能
- ✅ ベンダー非依存

**デメリット:**
- ✗ 初期開発コストが高い
- ✗ 運用・保守が必要
- ✗ スケーラビリティは自前で実装

**コスト:** 月額 $10-30（100件規模）

### 3.3 ✅ 推奨: ハイブリッドアプローチ

```
レイヤー1: 自社メタデータ検索エンジン（高速・低コスト）
    ↓ 候補テーブルを絞り込み
レイヤー2: Athena実データ検索（必要時のみ）
```

**検索フロー:**
1. ユーザーが「人口」で検索
2. キーワード辞書で展開: 「人口」→「population, 人口統計, demographics, 国勢調査」
3. メタデータカタログを検索（<100ms、無料）
4. 候補データセット5件を表示
5. 必要に応じてAthenaで実データ検索

**メリット:**
- ✅ 高速（メタデータ検索）
- ✅ 低コスト（必要時のみAthena実行）
- ✅ 柔軟性（日本語最適化）
- ✅ スケーラブル（AWS基盤）

**コスト:** 月額 $30-50（100件規模）

## 4. 時間データの扱い

### 4.1 問題: E-statの時間表現の多様性

E-statの`@time`フィールドは10種類以上の形式が存在:

```
"2020"           # 年のみ
"2020Q1"         # 四半期
"2020-01"        # 年月
"2020-01-01"     # 年月日
"202001"         # 年月（区切りなし）
"2020年度"       # 年度（日本語）
"令和2年"        # 和暦
"2020CY"         # 暦年
"2020FY"         # 会計年度
"2020H1"         # 半期
```

### 4.2 TIMESTAMP型の問題

**エラー例:**
```python
datetime.fromisoformat("2020")    # ValueError
datetime.fromisoformat("2020Q1")  # ValueError
datetime.fromisoformat("令和2年")  # ValueError
```

**情報損失:**
```
"2020Q1" → "2020-01-01" に変換
→ 四半期情報が失われる
```

### 4.3 ✅ 推奨: STRING型 + 補助カラム

```python
# スキーマ設計
{
    "time_original": "2020Q1",      # STRING: 元の表現
    "time_year": 2020,              # INT: 年
    "time_month": None,             # INT: 月
    "time_quarter": 1,              # INT: 四半期
    "time_type": "quarter",         # STRING: タイプ
    "time_sort_key": "2020-01-01"   # STRING: ソート用
}
```

**メリット:**
- ✅ すべての時間表現に対応（エラーゼロ）
- ✅ 元の表現を保持（情報損失ゼロ）
- ✅ クエリが柔軟（年、四半期、月で検索可能）
- ✅ シンプルな実装

**クエリ例:**
```sql
-- 年での検索
SELECT * FROM dataset WHERE time_year = 2020;

-- 四半期での検索
SELECT * FROM dataset WHERE time_year = 2020 AND time_quarter = 1;

-- 範囲検索
SELECT * FROM dataset 
WHERE time_sort_key BETWEEN '2020-01-01' AND '2020-12-31'
ORDER BY time_sort_key;
```

## 5. バッチ処理の実装

### 5.1 動的スキーマでもバッチ処理は可能

```python
# 100件を5並列でバッチ処理
orchestrator = DynamicIngestionOrchestrator(...)

results = orchestrator.ingest_datasets_batch(
    datasets=datasets,  # 100件
    max_concurrent=5    # 5並列
)
```

### 5.2 処理フロー（データセットごと）

```
1. データ取得（E-stat API）
   ↓
2. サンプルデータからスキーマ自動推論
   ↓
3. Icebergテーブル作成（データセット固有スキーマ）
   ↓
4. データ変換・ロード
   ↓
5. メタデータカタログに登録
```

**処理時間:** 平均 30-60秒/データセット（並列実行）

## 12. Q&A

### Q1: なぜ11ドメイン固定スキーマではダメなのか？

**A:** E-statのデータセットは非常に多様で、固定スキーマに押し込めると情報が失われます。例えば、国勢調査データには10個のカテゴリカラムがありますが、固定スキーマでは3-4個しか保存できません。動的スキーマなら全情報を保持できます。

### Q2: テーブル数が100個になると管理が大変では？

**A:** メタデータカタログで一元管理するため、ユーザーは個別のテーブルを意識する必要がありません。検索インターフェースから統一的にアクセスできます。

### Q3: バッチ処理は本当に可能か？

**A:** 可能です。各データセットの処理は独立しているため、並列実行が容易です。実装済みのオーケストレーターで5並列処理を実現しています。

### Q4: TIMESTAMP型を使わないとクエリが遅くならないか？

**A:** STRING型でも補助カラム（time_year, time_quarterなど）にインデックスを張ることで、TIMESTAMP型と同等のパフォーマンスを実現できます。むしろパースエラーがなくなる分、安定性が向上します。

### Q5: 自社検索ツールの開発コストは？

**A:** 基本実装は1-2週間で完成します。既にプロトタイプコードを提供しているため、カスタマイズのみで済みます。

### Q6: AWS既存ツールだけではダメか？

**A:** 基本的な検索は可能ですが、日本語キーワード変換や同義語展開などの高度な機能は自社実装が必要です。ハイブリッドアプローチなら両方の利点を活かせます。
