# E-stat全データ取得・データレイク構築計画

## 現状分析

### 達成済み
- ✅ 11ドメイン × 3データセット = 33データセット
- ✅ 約380万レコード
- ✅ MCPサーバー経由の自動取得パイプライン構築
- ✅ Iceberg形式でのデータ管理
- ✅ Athenaでのクエリ基盤

### 学んだこと
1. **大規模データセット対応**: 並列取得で100万レコード超のデータセットも処理可能
2. **API制限**: E-stat APIは1回10万レコードまで、並列取得で対応
3. **超大規模データ**: 1000万レコード超（消費者物価指数）は別途戦略が必要
4. **処理時間**: 33データセット取得に約17分（平均30秒/データセット）

## 計画オプション

### オプション1: 段階的拡張（推奨）
**目標**: 各ドメイン10データセット（合計110データセット）

**メリット**:
- 管理可能な規模
- 段階的な品質確認
- コスト予測可能

**スケジュール**:
- フェーズ1（1週間）: 各ドメイン+2データセット（55データセット）
- フェーズ2（1週間）: 各ドメイン+5データセット（110データセット）
- フェーズ3（継続）: 重要データセットの追加

**推定コスト**:
- S3ストレージ: 約10-50GB（$0.25-1.25/月）
- Athenaクエリ: 使用量に応じて

---

### オプション2: ドメイン集中型
**目標**: 重要3-5ドメインを完全網羅

**対象ドメイン候補**:
1. Labor（労働）- 雇用統計の完全セット
2. Economy（経済）- 経済指標の完全セット
3. Population（人口）- 人口統計の完全セット
4. Health（保健）- 医療統計の完全セット
5. Education（教育）- 教育統計の完全セット

**メリット**:
- 特定分野での深い分析が可能
- データ品質の高い維持
- 専門的な利用価値

---

**目標**: E-stat APIで取得可能な全データセット

**課題**:
- データセット数: 推定数千～数万
- データ量: 推定数十GB～数百GB
- 処理時間: 推定数日～数週間
- コスト: S3ストレージ $10-100/月

**必要な追加開発**:
- データセット自動発見機能
- バッチ処理システム
- エラーリカバリー機能
- 進捗モニタリング

### フェーズ1: 各ドメイン5データセット（55データセット）

#### 1.1 データセット選定基準
```yaml
優先順位:
  高: 
    - 更新頻度が高い（月次・四半期）
    - データ量が適度（10万～100万レコード）
    - 利用価値が高い（基幹統計）
  中:

    - データ量が大きい（100万～1000万レコード）

    - 更新頻度が低い
    - 特殊用途
```

   - 進捗レポート機能

   - 段階的実行（1日5-10データセット）
   - 品質チェック
   - エラー対応

4. **検証とドキュメント**（1日）
   - データ品質検証
   - マッピング更新
   - レポート作成

#### 1.3 推定リソース
- **時間**: 1週間
- **データ量**: 約5-20GB
- **レコード数**: 約500万～2000万レコード追加

## 技術的考慮事項

### 1. API制限対策
```yaml
E-stat API制限:
  - 1回のリクエスト: 最大10万レコード
  - レート制限: 要確認（推定: 数秒に1回）
  
対策:
  - 並列取得の活用
  - リトライロジック
  - レート制限の遵守
```

### 2. 大規模データセット対応
```yaml
サイズ別戦略:
  小規模（<10万）: 
    - 単一リクエストで取得
  中規模（10万～100万）:
    - 並列取得（3-10チャンク）
  大規模（100万～1000万）:
    - 並列取得（10-100チャンク）
    - バッチ処理
  超大規模（>1000万）:
    - フィルタリング取得
    - サンプリング
    - 別途戦略
```

### 3. データ品質管理
```yaml
品質チェック:
  - スキーマ検証
  - NULL値チェック
  - 重複チェック
  - 時系列整合性
  - ドメイン間整合性
```

### 4. コスト最適化
```yaml
S3最適化:
  - Parquet圧縮
  - パーティショニング戦略
  - ライフサイクルポリシー（古いデータをGlacierへ）

Athena最適化:
  - パーティションプルーニング
  - 列指向クエリ
  - 結果キャッシュ活用
```
